# ORG-004: Verify each tournament player's email

Status: COMPLETE
Team: Lead
Service: Tournaments

## Request and constraints

The user confirmed that the team captain enters each player's email in the
tournament registration form, and every entered address receives its own
verification code. Preserve the existing layout, signup and payment functionality.

## Contract

Tournament setup includes `requirePlayerEmailVerification`, a boolean frozen
after publication. Existing events default to false; the creation form enables
the option by default. Required events need exactly `teamSize` different player
emails. Optional events accept up to that count, including no emails.

- `POST /api/tournaments/{id}/player-emails/request-code` accepts `{email}` and
  returns `{email,challengeId,expiresIn,message}` after successful delivery.
- `POST /api/tournaments/{id}/player-emails/verify-code` accepts
  `{email,challengeId,code}` and returns `{email,challengeId,verified:true,expiresIn}`.
- Registration POST/PATCH accepts `playerEmails:[{email,challengeId?}]`. New or
  changed emails require verified, unexpired proofs. Editing may reuse emails
  already verified for that registration without a new challenge.
- Only the captain's own registration and the organisation's private roster
  expose `playerEmails:[{email,verified,verifiedAt}]`.

Codes have six digits, expire after ten minutes and are stored as password
hashes. Challenges are bound to the captain, tournament and exact email, limited
to five attempts and consumed only by a successful registration. Requests have
resend cooldown and shared recipient, captain and IP limits. Email transport
runs outside database transactions. Failed sends retain earlier usable codes;
failed registrations do not consume successfully verified proofs.

Existing Gmail, Resend and SMTP settings deliver a tournament-specific email.
No codes are included in API responses, public records, browser storage or logs.
No real player emails are used in automated checks.
